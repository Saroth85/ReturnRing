# ReturnRing

ReturnRing is a return-decision assistant for EU fashion merchants. It combines statistical
models for return propensity, abuse risk, customer value and product anomalies with a rules
engine, a net-benefit simulator, and Gemma 4 explanations and message drafts. A person approves
every restrictive action.

Built for the AMD Developer Hackathon ACT III, Track 3. The source of truth for behavior is
[docs/spec.md](docs/spec.md); architecture decisions live in [docs/adr/](docs/adr/README.md).

## Live demo

**[Open the live demo](https://returnring-demo-production.up.railway.app/demo)** — a read-only
Railway deployment with a synthetic serving snapshot. It runs `DEMO_MODE=live` and uses AMD Token
Factory for the investigator; saved drafts retain their recorded provenance. Some initial drafts
were validated through Gemma, while others retain mock provenance. See the
[Railway demo guide](docs/railway-demo.md) for the deployment and verification details.

## What the system does

- `apps/api` — FastAPI application and business services
- `apps/ui` — React + Vite browser app
- `pipeline` — offline generation, features, graph and serving export
- `ml` — training, evaluation and batch scoring
- `policy` — decision engine, legal guard and simulator
- `llm` — prompts, client, validator and message generation
- `contracts` — SQL schema, JSON schemas, IO and shared contract helpers

## Key guarantees

- The LLM never decides or predicts; scores come from `ml/` and admissible actions from
  `policy/engine.py`.
- The 14-day right of withdrawal is never denied; defects and non-conformity use the guarantee
  path before scoring (`policy/legal_guard.py`).
- Every restrictive action needs a human approver and a review date.
- Running services never read `data/truth/`; offline training and evaluation jobs do.
- Customer value never feeds the risk score.
- Numbers shown carry their origin, period and nature (real, synthetic or simulated).

## Quick start

You need Docker with Compose v2, GNU make and about 8 GB of RAM. On 14 Oct 2026, the API process
held about 1.6 GB after warm-up and peaked at up to about 2.2 GB during the demo walk (full
synthetic store, host process, not in a container; real timing, measured once).

```bash
cp .env.example .env
make demo-data
make dev-up
```

Then open **http://localhost:8080**. This starts the CPU demo with the deterministic mock LLM
(`DEVICE=cpu`, `LLM_MODE=mock`).

| Command | What it does |
| --- | --- |
| `make reset` (dev) or `make demo-reset` (cached) | resets the demo state; do this before `make demo-walk` |
| `make demo-walk` | walks the demo over HTTP and checks the contract |
| `make dev-logs`, `make dev-down` | shows logs, stops the stack |
| `make test`, `make lint`, `make licenses` | runs CPU tests, Ruff/mypy and the Python licence gate |

## Demo modes

### Cached demo

The cached replay is a separate, local mode (`DEMO_MODE=cached`) with the GPU containers off. It
serves saved drafts from a package generated by local vLLM; it is not the live Railway demo.
The API labels drafts **"Precomputed on AMD MI300X"** only when the package manifest verifies
that provenance. Other packages, such as CPU rehearsals, use
**"Precomputed in a rehearsal, not verified on AMD MI300X"**. Read-only access is controlled
separately by `PUBLIC_READ_ONLY` (on by default in the cached Compose profile).

The package contains a serving snapshot, saved drafts, benchmark results and a `MANIFEST.json`
with file hashes and per-draft model and hardware provenance. `make demo-export` requires an
explicit `DEMO_GPU` value and a batch for `GEMMA_MODEL`; it refuses an unverified GPU batch unless
`REHEARSAL=1`. The cached package is intended for a local replay; when the MI300X package is
published, its release asset will be linked here. Until then, the laptop path is for the team:

```bash
make demo-import
make demo-local
make demo-reset
make demo-down
```

These packaging targets use host `python3` (Python 3.8 or later, standard library only).

### Live AMD inference

For live AMD inference, set `LLM_MODE=tokenfactory`, `RADEON_API_KEY` and `DEMO_MODE=live`.
Token Factory receives synthetic demo inputs only. The application settings reject Token Factory
with `DEMO_MODE=cached` because the cached drafts have separate, recorded provenance.

### The GPU session

Training and benchmark jobs run separately from the API and UI. The GPU runbook is
[infra/spikes/README.md](infra/spikes/README.md). On a public GPU deployment, basic auth on the
telemetry data and the writes protects the admin operations; the public demo views have their
separate read-only setting.

## How the risk is computed

See the [risk-model method](docs/risk-model.md) and
[measured results](docs/results/us-204-risk.md). Defect or non-conformity returns take the
guarantee path before scoring. Abuse risk is estimated from decision-time behavior, account-graph
evidence and the residual against a product/cohort reference model, never a personalized
predictor. Customer value places a case in a quadrant but is never an abuse signal. Return
probability at checkout is trained on real ASOS data.

| Figure | Value | Origin | Period | Nature |
| --- | --- | --- | --- | --- |
| Customer risk model A3, AUPRC on held-out test customers | 0.980 (6,009 customers, 271 abusive) | main synthetic store, [risk results](docs/results/us-204-risk.md) | features at 2026-10-01, store 2025-10-01..2026-09-30 | synthetic |
| The same model on the out-of-distribution store | AUPRC 0.840; promo-ring recall 0.363 | OOD store (US-105), never used to train | same | synthetic |
| Rules-only baseline A0, same rows | AUPRC 0.633 | main synthetic store | same | synthetic |
| Return probability, decision-time protocol B | F1 0.739 against 0.721 for the best one-feature rule | ASOS GraphReturns test split, [propensity results](docs/results/us-201-propensity.md) | 2021-10-01..2021-11-30 | real |
| GraphSAGE embeddings added to A3 (A4) | AUPRC 0.977, a regression of 0.003 | main synthetic store | features at 2026-10-01 | synthetic |

Synthetic abuse metrics measure consistency with generator hypotheses, not real-world abuse
detection. The OOD promo-ring recall is 0.363 (synthetic, features at 2026-10-01); FAIR-02 has
a 6.78-point false-positive gap between main product categories (synthetic, held-out test
customers at 2026-10-01). These regressions are reported as measured.

## Architecture at a glance

- The API reads a verified `serving/` snapshot, not raw ground truth.
- Decision-time features are built before request scoring.
- The UI is split into operator, agent, manager and platform areas.
- API and UI contracts are shared through `contracts/`.
- In local development, `LLM_MODE=mock` makes no model calls outside the machine. Deployments
  explicitly select local vLLM or Token Factory.

## Limits, declared

- Abuse is simulated; linked-account behavior is a design hypothesis calibrated on real ASOS
  aggregates. Detection must be verified with a real merchant.
- GraphSAGE is slightly worse than A3 here (AUPRC 0.977 vs 0.980), and OOD ring recall is low.
- FAIR-02 fails: the false-positive gap is 6.78 points, above the 5-point limit.
- LLM free-text checks are blocklists; a paraphrase can evade them. Customer messages use
  reviewed sentences and code-owned fields, and restrictive actions need human approval.
- GPU results are pending. Legal constraints need review by a consumer-law professional before
  real use; they are not legal advice.
